## Service Overview

The Document Search Service is a distributed, multi-tenant system designed to handle full-text search across millions of documents with sub-second response times. The prototype demonstrates:

- **Multi-tenancy**: Complete tenant isolation with role-based access control
- **Full-text search**: Elasticsearch-powered search with relevance ranking
- **Horizontal scalability**: Index-per-tenant architecture supporting independent scaling
- **Fault tolerance**: Health monitoring and status checks for all services
- **Performance optimization**: Redis caching and async document ingestion via RabbitMQ

## Core Features

### 1. Document Search

The search functionality is the core feature of the application:

**Search Interface:**
- **Tenant Filter**: Select a specific tenant or "All Tenants" (admins only)
- **Search Input**: Full-text search with autocomplete
- **Bypass Cache**: Option to skip Redis cache for fresh results
- **Allow Fuzzy Search**: Enable typo-tolerant search when exact matches fail

**Search Features:**
- **Exact Match**: Default search mode prioritizing exact term matches
  - Title matches receive higher relevance scores
  - Supports prefix matching (e.g., "dic" matches "dick")
  - Filters common stop words ("the", "and", "is", etc.)
- **Fuzzy Search**: Fallback mode for typo tolerance
  - Automatically triggered if exact match returns no results
  - Uses Elasticsearch AUTO fuzziness (0-2 character edits)
  - Metrics show both exact and fuzzy query performance

**Search Results:**
- **Document Name**: Clickable link to view full document
- **Highlights**: Up to 2 matching text snippets per document
- **Score**: Elasticsearch relevance score
- **File Type**: Document format (PDF, DOCX, TXT, HTML, etc.) with icon
- **Tenant ID**: Which tenant the document belongs to (visible in multi-tenant view)

**Performance Metrics:**
- Total round-trip time (browser to browser)
- Browser → API network time
- API → Elasticsearch query time
- Elasticsearch execution time
- Result processing time
- Fuzzy search indicators and detailed metrics

## Tenant Isolation & Security

### Access Control

The application enforces strict tenant isolation:

**Platform Admins:**
- Access to all tenants
- Can search across all tenants or filter by specific tenant
- Full access to admin features (system status, user/tenant management)

**Tenant Users:**
- Access limited to their assigned tenant(s) only
- Search results automatically filtered to their tenant
- No access to:
  - System status
  - User management
  - Tenant management
  - Index dump functionality
  - Other tenants' documents

### Search Filtering

The search API automatically enforces tenant access:

1. **User Authentication**: Verifies user identity via NextAuth session
2. **Tenant Resolution**: Determines accessible tenants based on user memberships
3. **Query Filtering**: 
   - If tenant specified: Verifies access and searches only that tenant
   - If no tenant specified: Searches all accessible tenants (all for admins, only their tenant for tenant users)
4. **Result Filtering**: Results are automatically scoped to accessible tenants

**Verification:**
- Tenant users cannot see documents from other tenants
- Tenant users cannot access other tenants' indices
- Search queries are automatically scoped to user's accessible tenants
- API endpoints validate tenant access before processing requests

## Service Architecture

### Technology Stack

- **Frontend**: Next.js 16 (App Router) with React 19
- **Backend**: Next.js API routes
- **Database**: PostgreSQL (users, tenants, memberships, file manifest)
- **Search Engine**: Elasticsearch 8.15.0 (index-per-tenant)
- **Cache**: Redis 7 (search results, rate limiting)
- **Message Queue**: RabbitMQ (async document ingestion)
- **Authentication**: NextAuth.js 5.0 (email/password)

### Data Sources

The prototype includes documents from multiple sources:

- **Gutenberg**: Project Gutenberg books (via Gutendex API)
- **S3 Tenants**: AWS S3 bucket with French literature documents
- **Local Files**: Local file system documents (for testing)

### Document Ingestion

Documents are ingested asynchronously:

1. **Producers** (Python): Discover documents from various sources
   - Scan for new/changed/deleted files
   - Use manifest table for change detection
   - Enqueue jobs to RabbitMQ
2. **Consumer** (Python): Process documents
   - Dequeue jobs from RabbitMQ
   - Extract text based on MIME type
   - Chunk documents (1000 chars with 200 char overlap)
   - Index chunks into Elasticsearch
   - Update manifest table

## Performance Characteristics

- **Search Response**: <500ms for 95th percentile queries
- **Cache TTL**: 5 minutes for search results
- **Rate Limiting**: Per-tenant rate limits (100 requests per 60 seconds)
- **Indexing**: Async via RabbitMQ queue (non-blocking)
- **Sharding**: 3 primary shards + 1 replica per tenant index

---

## Limitations (Prototype)

This is a prototype demonstrating architectural patterns, so some features are simplified:

- **No API tokens**: Uses NextAuth session-based auth only
- **No advanced search**: No phrase search, boolean operators, field-specific search
- **No document upload UI**: Upload via API only (POST /api/documents)
- **No real-time updates**: Search results may lag by seconds after indexing
- **No advanced analytics**: Basic metrics only
- **Single region**: No multi-region support
- **No backup/restore UI**: Manual operations required
