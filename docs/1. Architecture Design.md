## High-Level System Architecture

### What You Asked

> "High-level system architecture diagram showing all major components"

### What I Understand

A distributed document search service needs to handle millions of documents with sub-second response times while maintaining tenant isolation. The architecture must support horizontal scaling, fault tolerance, and efficient search operations.

### What We Should Do in Production

A production system would include:
- **Load balancers** for traffic distribution
- **Multiple application instances** behind the load balancer
- **Elasticsearch cluster** with dedicated master, data, and ingest nodes
- **PostgreSQL primary-replica** setup for read scaling
- **Redis cluster** for high availability caching
- **Message queue cluster** (RabbitMQ with HA queues)
- **CDN** for static assets
- **Monitoring stack** (Prometheus, Grafana, ELK)
- **Service mesh** for inter-service communication

## Database/Storage Strategy

### What You Asked

> "Database/storage strategy (explain your choice of search engine, database, cache layers)"

### What I Understand

Different data types require different storage solutions. Relational data needs ACID guarantees, search needs full-text capabilities, and caching needs speed.

### What We Should Do in Production

- **PostgreSQL**: Primary database with read replicas, connection pooling, query optimization
- **Elasticsearch**: Dedicated cluster with proper sizing, index lifecycle management, snapshot backups
- **Redis**: Cluster mode for HA, persistence options (AOF + RDB), memory optimization
- **Object Storage**: S3-compatible storage for large files, CDN integration
- **Backup Strategy**: Point-in-time recovery, cross-region replication

### What I Did in This Prototype

#### PostgreSQL (Relational Data)

**Why PostgreSQL:**
- ACID compliance for user/tenant data
- Strong consistency requirements
- Rich query capabilities
- Mature ecosystem (Prisma ORM)

**What We Store:**
- Users, tenants, memberships (access control)
- File manifest (change detection, idempotency)

**Code Evidence:**
- Schema: `apps/web/prisma/schema.prisma`
- Client: `apps/web/src/lib/prisma.ts`

#### Elasticsearch (Search Engine)

**Why Elasticsearch:**
- **Full-text search**: Advanced querying (fuzzy, phrase, boolean)
- **Relevance ranking**: TF-IDF, BM25 scoring
- **Horizontal scalability**: Shard-based distribution
- **Index-per-tenant**: Natural isolation
- **Performance**: Sub-second queries on millions of documents

**Index Strategy:**
- One index per tenant: `docs_{tenant_slug}`
- **Sharding Configuration**: 3 primary shards + 1 replica per index
  - **Why 3 shards**: Allows horizontal scaling across 3 nodes
  - **Why 1 replica**: Provides fault tolerance and read scaling
  - **Prototype rationale**: Demonstrates production-ready sharding strategy
  - **Production**: Would scale to 5-10 shards for very large tenants
- **Chunked documents**: 1000 chars per chunk, 200 char overlap
  - **Chunking Strategy**: See "Document Chunking Strategy" section below

**Code Evidence:**
- Index creation: `apps/web/src/lib/elasticsearch.ts:27-100`
- Shard config: `apps/web/src/lib/elasticsearch.ts:38-39`

#### Redis (Caching)

**Why Redis:**
- **Speed**: In-memory, sub-millisecond latency
- **TTL support**: Automatic expiration
- **Atomic operations**: Rate limiting counters
- **Simple**: Easy to integrate

**What We Cache:**
- Search results (5-minute TTL)
- Per-tenant cache keys to prevent collisions

**Code Evidence:**
- Cache key generation: `apps/web/src/lib/redis.ts:20-22`
- Cache usage: `apps/web/src/app/api/search/route.ts:100-150`

## Consistency Model and Trade-offs

### What You Asked

> "Consistency model and trade-offs"

### What I Understand

Different parts of the system have different consistency requirements. User data needs strong consistency, search can tolerate eventual consistency.

### What We Should Do in Production

- **Strong consistency**: User/tenant data (PostgreSQL with transactions)
- **Eventual consistency**: Document indexing (async processing)
- **Read-after-write**: Search results may lag by seconds
- **Conflict resolution**: Last-write-wins for document updates
- **Idempotency**: All operations must be safe to retry

### What I Did in This Prototype

**Consistency Model:**

1. **Strong Consistency (PostgreSQL)**
   - User authentication, tenant membership
   - File manifest (prevents duplicate indexing)
   - ACID transactions for critical operations

2. **Eventual Consistency (Elasticsearch)**
   - Document indexing via async queue
   - Search results may lag by seconds
   - Acceptable trade-off for performance

3. **Trade-offs:**
   - **Performance vs. Consistency**: Async indexing = faster API responses
   - **Availability vs. Consistency**: Elasticsearch can be eventually consistent
   - **Simplicity vs. Complexity**: Single-node ES for prototype vs. cluster in production

**Code Evidence:**
- Manifest check: `workers/python/manifest.py`
- Async indexing: `workers/python/consumer.py`

### Manifest Table Interactions

### What You Asked

> "How the manifest table couples with producers, API calls (delete, reindex)"

### What I Understand

The `file_manifest` table in PostgreSQL is the source of truth for document state. It coordinates between producers (change detection), API calls (delete, reindex), and prevents duplicate processing.

### What We Should Do in Production

- **Distributed locking**: Prevent concurrent manifest updates
- **Audit logging**: Track all manifest changes
- **Reconciliation jobs**: Periodically verify manifest vs. Elasticsearch
- **Manifest replication**: For multi-region deployments
- **Backup strategy**: Point-in-time recovery of manifest state

### What I Did in This Prototype

**Manifest Table Interactions:**

```text
┌─────────────────────────────────────────────────────────────┐
│              PostgreSQL (file_manifest table)               │
│  ┌──────────────────────────────────────────────────────┐  │
│  │  Columns: tenantId, path, documentId, mtime, size,   │  │
│  │           contentHash, etag, isDeleted, lastIndexed   │  │
│  └──────────────────────────────────────────────────────┘  │
└──────┬──────────────┬──────────────┬───────────────────────┘
       │              │              │
       │              │              │
       │              │              │
┌──────▼──────┐ ┌─────▼──────┐ ┌────▼──────────────┐
│  Producers  │ │ API Calls   │ │  Consumer         │
│             │ │             │ │                   │
│ 1. Scan     │ │ DELETE      │ │ 1. Process upsert │
│    sources  │ │ /documents/  │ │    - Read manifest│
│             │ │ {id}         │ │    - Index chunks │
│ 2. Compare  │ │              │ │                   │
│    with     │ │ - Delete from│ │ 2. Process delete │
│    manifest │ │   ES         │ │    - Delete chunks│
│             │ │              │ │                   │
│ 3. Detect   │ │ - Mark       │ │ 3. Update manifest│
│    changes  │ │   isDeleted  │ │    (lastIndexed)  │
│    (new/    │ │   = true     │ │                   │
│    changed/ │ │              │ │                   │
│    deleted) │ │ DELETE       │ │                   │
│             │ │ /tenants/    │ │                   │
│ 4. Enqueue  │ │ {slug}/index │ │                   │
│    upsert/  │ │              │ │                   │
│    delete   │ │ - Delete ES  │ │                   │
│             │ │   index      │ │                   │
│ 5. Update   │ │              │ │                   │
│    manifest │ │ - Option 1:  │ │                   │
│    (insert/ │ │   DELETE     │ │                   │
│    update)  │ │   manifest   │ │                   │
│             │ │   entries     │ │                   │
│             │ │   (allows     │ │                   │
│             │ │   reindex)    │ │                   │
│             │ │              │ │                   │
│             │ │ - Option 2:  │ │                   │
│             │ │   Mark       │ │                   │
│             │ │   isDeleted  │ │                   │
│             │ │   = true     │ │                   │
│             │ │   (prevents  │ │                   │
│             │ │   reindex)    │ │                   │
└─────────────┘ └──────────────┘ └───────────────────┘
```

**Key Interactions:**

1. **Producers → Manifest**:
   - **Read**: Query manifest to detect changes (compare mtime, size, hash)
   - **Write**: Insert new entries, update changed entries, mark deleted entries
   - **Code**: `workers/python/manifest.py`, `workers/python/*_producer.py`

2. **API DELETE → Manifest**:
   - **DELETE /api/documents/{id}**: Marks manifest entry as `isDeleted = true`
   - **Prevents reindexing**: Producer skips files marked as deleted
   - **Code**: `apps/web/src/app/api/documents/[id]/route.ts:101-190`

3. **API Reindex → Manifest**:
   - **DELETE /api/tenants/{slug}/index**:
     - **Option 1 (clearManifest=true)**: DELETE all manifest entries → allows full reindex
     - **Option 2 (clearManifest=false)**: Mark `isDeleted = true` → prevents reindex
   - **Code**: `apps/web/src/app/api/tenants/[slug]/index/route.ts:170-239`

4. **Consumer → Manifest**:
   - **Read**: Query manifest to get document metadata
   - **Write**: Update `lastIndexed` timestamp after successful indexing
   - **Code**: `workers/python/consumer.py:133-380`

**Benefits:**
- ✅ **Idempotency**: Same file won't be indexed twice (unless changed)
- ✅ **Change Detection**: Only changed files are processed
- ✅ **Delete Coordination**: API deletes sync with producer scans
- ✅ **Reindex Control**: Can clear manifest to force reindex, or mark deleted to prevent it

**Code Evidence:**
- Manifest class: `workers/python/manifest.py`
- Producer usage: `workers/python/s3_producer.py:100-200`
- API delete: `apps/web/src/app/api/documents/[id]/route.ts:101-190`
- API reindex: `apps/web/src/app/api/tenants/[slug]/index/route.ts:170-239`

## Message Queue Usage

### What You Asked

> "Message queue usage for asynchronous operations"

### What I Understand

Document ingestion can be slow (download, extract, chunk, index). Using a message queue decouples the API from processing, improving responsiveness.

### What We Should Do in Production

- **Multiple queues**: Priority queues, dead letter queues
- **Message persistence**: Durable queues, message acknowledgments
- **Scaling**: Multiple consumers, auto-scaling based on queue depth
- **Monitoring**: Queue depth, processing rate, error rate
- **Retry logic**: Exponential backoff, max retries

### What I Did in This Prototype

**RabbitMQ Usage:**

- **Queue**: `doc_ingest`
- **Producers**: Discover documents, enqueue jobs
- **Consumer**: Process documents (download, extract, chunk, index)
- **Message Format**: JSON with document metadata and source URL

**Code Evidence:**
- Producer: `workers/python/s3_producer.py:100-200`
- Consumer: `workers/python/consumer.py:50-150`
- Queue config: `docker-compose.yml`

**Benefits:**
- API responds immediately (doesn't wait for indexing)
- Can scale consumers independently
- Failed jobs can be retried

## Multi-Tenancy Approach and Data Isolation

### What You Asked

> "Multi-tenancy approach and data isolation strategy"

### What I Understand

Tenant isolation is critical for security and compliance. Data must be completely isolated between tenants.

### What We Should Do in Production

- **Database-level isolation**: Separate databases per tenant (highest isolation)
- **Schema-level isolation**: Separate schemas per tenant
- **Row-level security**: Shared tables with tenant_id filtering
- **Application-level isolation**: Index-per-tenant (what we use)
- **Network isolation**: VPCs per tenant (enterprise)
- **Encryption**: Tenant-specific encryption keys

### What I Did in This Prototype

**Index-Per-Tenant Pattern:**

- Each tenant has isolated Elasticsearch index: `docs_{tenant_slug}`
- API enforces access control (users can only access their tenants)
- Cache keys include tenant ID
- Rate limiting per tenant

**Access Control:**
- **Platform Admin**: Can access all tenants
- **Tenant User**: Can only access their assigned tenant
- Enforced at API layer: `apps/web/src/lib/auth-helpers.ts`

**Code Evidence:**
- Index naming: `apps/web/src/lib/elasticsearch.ts:20-22`
- Access check: `apps/web/src/lib/auth-helpers.ts:50-80`
- Search filtering: `apps/web/src/app/api/search/route.ts:72-85`

**Benefits:**
- Natural isolation (separate indexes)
- Easy to scale per tenant
- Simple to understand and maintain

**Trade-offs:**
- More indexes to manage (acceptable for prototype)
- Cross-tenant search requires querying multiple indexes (handled in code)
